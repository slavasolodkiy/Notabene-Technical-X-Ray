## 1\. Audit Scope, Method, and Overall Verdict

### 1.1 What was audited and how

#### 1.1.1 Object of audit

The artifact under audit is Replit's *Technical X-Ray* of Notabene (notabene.id), produced against a 15-phase public-evidence investigation brief. It comprises three deliverables: the report body (TECHNICAL\_REPORT.md plus action log and final summary), a 25-question list for Notabene (QUESTIONS\_FOR\_NOTABENE.md), and a live single-page application at [notabene-id-technical-x-ray.replit.app](https://notabene-id-technical-x-ray.replit.app/) (React \+ Vite; all content ships in one 4.6 MB `evidence.json`; fetched 2026-09-24). All three are measured against the brief's phase requirements and the primary public record; claim-level verdicts are consolidated in the corrections register (§2).

#### 1.1.2 Method

Five parallel primary-source verification tracks were executed, each re-fetching its artifacts on 2026-09-24 and ruling on Replit's claims on the four-value scale defined in §2: **CONFIRMED**, **CORRECTED**, **REFUTED**, or **UNVERIFIABLE** (downgraded to UNKNOWN). Facts about Notabene's platform are separately labeled VERIFIED, INFERRED, or UNKNOWN, mirroring the report's own labeling discipline. Operation counts were produced by counting path×method over the keys {get, post, put, patch, delete} in the parsed specifications; legal claims were checked against verbatim regulation text; package and repository inventories were enumerated from registry and group APIs, not documentation.

### 1.2 Overall verdict

#### 1.2.1 What holds

All seven jurisdiction-versus-law cross-checks (J1–J7) reproduce from verbatim primary text, including the GB staleness finding — reg 64C(4) now reads "equal to or exceeds … £800" (substituted 30.6.2026 by SI 2026/621) while the vendor index still matches the superseded "1,000 euros" text ([legislation.gov.uk](https://www.legislation.gov.uk/uksi/2017/692/regulation/64C), fetched 2026-09-24). The token chain (24-hour institution token, 5-minute customerToken, delegate JWT with unpublished TTL), the managed/E2E/escrow encryption-mode scoping, the DIDComm repudiation distinction, the V1/V2 IVMS101 field renames, and the TAP license conflict (repo CC0-1.0 vs README CC BY-SA 4.0) are all CONFIRMED (§2, rows 8–9, 11–19).

#### 1.2.2 What is wrong

Four claims fail. "157 API operations" is not reproducible: V2 \= 105 confirmed, but V1 \= 126, not 52, and no documented scoping yields 52 (combined \= 231). "Four npm packages" is refuted: eight scoped packages exist. V1 amounts are base-unit **strings** ("satoshi, wei, etc", example `"10000000000000000"`), not integers — a type error that breaks client generators above 2^53 (1 ETH \= 10^18 wei). "Micro-transfers require the institution to verify them" is documented nowhere and is downgraded to UNKNOWN. The "223 archived pages" evidence corpus is REFUTED as served: filenames appear in the app's Sources table but no archive path is retrievable.

#### 1.2.3 What is missing or thin

Four gaps are structural rather than erroneous. Phase 12 code archaeology is nearly absent from the report body beyond the observation that the NodeJS SDK is V1-shaped; this audit supplies it (§6). Japan was left UNKNOWN and is now resolved (§4). The brief's worked identity example (Bank A→Alice→Exchange B→Bob) is absent from the report body, though it exists in the app's Actor Map content. And the System Map and Actor Map nav items serve byte-identical copies of the Product Map and ER Diagram — placeholder content, not the distinct analyses the brief requested (§7).

#### 1.2.4 Editorial defects

Four assembly defects must be corrected for the document to be trustworthy. **(D1)** The method section states "this draft deliberately omits operation and field-path totals while extraction is being finalized" ([report under audit](https://replit.com/@identityglobal/Notabene-Technical-X-Ray), fetched 2026-09-24) — directly contradicting the report's own advertised "157 API operations" and "3,905 field-path records." **(D2)** A duplicated citation marker `[3] [3]` appears in the method paragraph. **(D3)** The source list labels GitLab and npm registry listings "Tier 1" under a taxonomy that reserves Tier 1 for law and regulator text; these are primary artifacts but belong in a distinct class. **(D4)** Verification debt is disclosed but easy to miss: only 18 of 20 probed links returned HTTP 200 (one 202, one anti-bot block), and 12 of 19 diagrams received only conservative syntax inspection after a DOMPurify failure — roughly 63% of the app's diagrams were never machine-validated.

### 3.2 V1↔V2 schema differences

#### 3.2.1 Amounts: decimal strings versus base-unit strings

Replit's report states that "V1 uses … base-unit integer amounts" while V2 uses decimal strings. The unit claim is **CONFIRMED**; the type claim is **CORRECTED**. In V2, the `amount` field of `POST /entities/{entityDID}/tx` is a string constrained by `"pattern": "^\\d+(\\.\\d+)?$"` with example `"1.5"`. In V1, `TransactionInformation.amount` is described as "Amount in base unit of the asset (satoshi, wei, etc)" but is typed `string`, not integer — the `/tx/create` example passes `"transactionAmount": "10000000000000000"` as a quoted string ([doc.notabene.id](https://doc.notabene.id/), fetched 2026-09-24). The distinction is not pedantic: a client that models V1 amounts as integers will overflow 53-bit IEEE-754 precision on an 18-decimal wei-denominated value (10¹⁶ exceeds 2⁵³), so both generations require string or arbitrary-precision handling, and the real migration change is decimal-units-plus-regex in V2 versus base-units in V1. Note also that the V2 Flow payout schema types `amount` as `string` with no decimal pattern enforced — the `^\d+(\.\d+)?$` constraint applies to the Transact transfer-create body, not to Flow.

#### 3.2.2 IVMS101 containers: plural arrays become singular, and one identifier type is renamed

V1 uses `originatorPersons` / `beneficiaryPersons` (plural; 7 occurrences each across the V1 spec); V2 uses `originatorPerson` / `beneficiaryPerson` (singular; 13 occurrences each), with zero cross-occurrences in either artifact. The V1 `/tx/create` example nests `originatorPersons: [{ naturalPerson: { name: [{ nameIdentifier: [{ primaryIdentifier: "Frodo", secondaryIdentifier: "Baggins", nameIdentifierType: "LEGL" }] }] } }]`. The embedded-components documentation additionally instructs integrators to rename three fields when transforming component output: `originatorPersons → originatorPerson`, `beneficiaryPersons → beneficiaryPerson`, and `nameIdentifierType → naturalPersonNameIdentifierType` ([devx.notabene.id](https://devx.notabene.id/docs/embedded-components-v2-api.md), fetched 2026-09-24). Despite the singular name, the V2 `originatorPerson` property is typed `anyOf [array, null]` in the transfer-create 201-response schema, so "singular" refers to the field name, not the cardinality — client models must still accept an array.

The matrix yields three distinct failure modes that an integrator must treat separately. #### 4.1.1 GB: SI 2026/621 substituted the threshold on 30 June 2026

The current revised text of regulation 64C(4) reads: "Where paragraph (3) does not apply and the transfer is equal to or exceeds the equivalent in cryptoassets of **£800** in value (taken together with any other cryptoasset transfer which appears to be linked), the cryptoasset business of the originator must ensure that the inter-cryptoasset business transfer is also accompanied by the information specified in paragraph (6)" ([legislation.gov.uk](https://www.legislation.gov.uk/uksi/2017/692/regulation/64C), fetched 2026-09-24; the page states it is "up to date with all changes known to be in force on or before 24 September 2026"). The page's amendment annotation identifies the instrument Replit's report did not name: "F2 Sum in reg. 64C(4) substituted (30.6.2026) by The Money Laundering and Terrorist Financing (Amendment) Regulations 2026 (S.I. 2026/621), regs. 1(2), 32". The superseded point-in-time version read "1,000 euros" ([legislation.gov.uk](https://www.legislation.gov.uk/uksi/2017/692/regulation/64C/2023-09-01), fetched 2026-09-24; "Version Superseded: 30/06/2026"). The vendor's GB entry — `"currency": "EUR"`, `GB-1000.json`, threshold "1000" — matches the superseded text exactly, which dates the definition's legal basis: it encodes the pre-30-June-2026 law. Replit's claim J1 is **CONFIRMED**, extended by the SI 2026/621 identification.  
The worked implication is concrete. Consider a UK originator VASP sending the equivalent of £850 to a German beneficiary VASP on 2026-09-24. Under 64C(4) as amended, £850 "equal to or exceeds" £800, paragraph (3) does not apply (the beneficiary business is not carrying on business in the UK), so the transfer must be accompanied by the paragraph (6) set — one of customer ID, address, passport/national-ID number, or date and place of birth — and 64C(9) prohibits execution before full compliance. Under the vendor index as published, the selector compares against EUR 1,000; at any plausible 2026 exchange rate £850 converts to roughly €980–€1,000, at or below the vendor trigger, so GB-0 (base fields only) can be selected and the transfer passes the vendor check without any paragraph (6) data. The same transfer is simultaneously vendor-compliant and in breach of 64C(4)/(9). Had the two businesses both been UK-based, the opposite error shape would apply: paragraph (6) information would be required only on beneficiary request within three working days (64C(2)–(3)), a branch the vendor artifacts do not model at all.

#### 4.1.2 EU: the EUR 1,000 threshold is not a Travel Rule exemption

Recital (30) of the TFR states that transfers of crypto-assets "should be subject to the same requirements regardless of their amount and of whether they are domestic or cross-border transfers" ([EUR-Lex](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32023R1113), fetched 2026-09-24). The EUR 1,000 figure appears only in Article 14(5) and Article 16(2), where a transfer "of an amount exceeding EUR 1 000" to or from a self-hosted address obliges the crypto-asset service provider to "assess whether that address is owned or controlled by" its client — an ownership-assessment trigger, not an information exemption. Article 14(1)(d) is the compound requirement: "the originator's address, including the name of the country, official personal document number and customer identification number, or, alternatively, the originator's date and place of birth". FR-0's OR requirement is `"rule": "pick", "count": 1` over four independent groups {dateAndPlaceOfBirth, customerIdentification, geographicAddress, nationalIdentification}. Supplying only a customer identification number satisfies FR-0 but does not satisfy limb 1 of Art 14(1)(d), which requires address-with-country AND document number AND customer ID together. Replit's claims J3 and J4 are **CONFIRMED**. The integrator consequence: for EU-originating transfers, the vendor definition must be treated as a floor on structure, not on content; a compliant engine enforces the compound limb itself.

#### 4.1.3 US: five PII fields against a seven-item statutory list

31 CFR 1010.410(f) applies to "a transmittal of funds in the amount of $3,000 or more" and lists at (f)(1): transmittor name and account number, transmittor address, "(iii) The amount of the transmittal order; (iv) The execution date of the transmittal order; (v) The identity of the recipient's financial institution", recipient details "as received", and "(vii) Either the name and address or numerical identifier of the transmittor's financial institution" ([eCFR](https://www.ecfr.gov/current/title-31/subtitle-B/chapter-X/part-1010/subpart-E/section-1010.410), fetched 2026-09-24). US-3000.json carries exactly five fields — originator name, geographicAddress, accountNumber; beneficiary name, accountNumber — with no amount, no execution date, and no financial-institution identifiers. Replit's claim J5 is **CONFIRMED**: the definition covers the IVMS101-shaped PII portion ((f)(1)(i), (ii), and partially (vi)) but is not the complete transmittal-order record. The threshold itself — 3000, inclusive comparator — is the one trigger in the matrix that matches current law exactly.

#### 4.1.5 JP: the open item closes — JP-0 is not stale

### 4.3 Presentation-definition mechanics

#### 4.3.1 Executable vendor logic, not law

All thirteen fetched definitions (GB-1000, GB-0, FR-0, SG-1500, SG-0, US-3000, US1-3000, US2-0, US0-0, JP-0, FA-1000, XX\_old-1000, XX\_old-0) share one mechanics, VERIFIED from the JSON. Each `input_descriptors[].constraints.fields[]` entry declares JSONPath expressions under `path` with `"predicate": "required"`; the vendor-specific object form `"path": {"natural": [...], "legal": [...]}` distinguishes natural-person from legal-person IVMS101 branches, and a field is satisfied when data exists at the applicable person-type branch. `submission_requirements` applies an outer `"rule": "all"` (conjunction) over `from_nested` entries, so the base group is always mandatory in full. Alternatives are expressed as a nested `{"name": "OR requirement", "rule": "pick", "count": 1}`, meaning exactly one listed group must be satisfied — and the chosen group is itself `"rule": "all"`, so every field of that one group must be present (choosing geographicAddress requires all of addressType, addressLine, streetName, buildingNumber, postCode, townName, country). Every descriptor carries `"limit_disclosure": "required"`. Net semantics, using FR-0: (originator name AND originator account AND beneficiary name AND beneficiary account) AND exactly one of {full address block, national-ID block, customer identification, date-and-place-of-birth pair}. Replit's claim J7 is **CONFIRMED**. These semantics are the vendor's executable encoding of its reading of each rule set; the A-not-B deltas in §4.1 are precisely the places where that encoding diverges from the legal text it approximates.  
The open UNKNOWNs that remain — each a production-blocking design input, none resolvable from public artifacts — are: precedence when the originator's and beneficiary's jurisdictions impose different definitions on the same transfer; the exchange-rate source, valuation instant, and rounding used to compare a crypto amount against a fiat threshold; linked-transfer aggregation (64C(4) requires it; no definition expresses it); immutable versioning of definitions and notification of customers when a definition or threshold changes; and, from Replit's own list, US below-threshold behavior and EU DLT-address/LEI placement. Until the vendor documents these, any engine built on the index must implement them locally and record its choices per transfer.

### 5.1 DID architecture confirmed with live evidence

#### 5.1.1 did:web issuance and hosting model — CONFIRMED (I1), with live resolution evidence

Replit's report states that an onboarded entity receives a `did:web` identity whose DID Document is self-hosted or redirected to a Notabene-hosted copy. The documentation supports this verbatim: "You will, when your company entity is created in the Notabene Network, be assigned your webDID… `did:web:{your domain}` Which will *resolve* to `https://{your domain}/.well-known/did.json`", and "Host the DIDdoc on your own domain or set up a redirect to the default one at Notabene \- note that this only works for hosted encryption" ([diddocs-explained](https://devx.notabene.id/docs/diddocs-explained.md), fetched 2026-09-24). First, both live service endpoints are QA hosts (`*.notabene.studio`); the production DIDComm endpoint pattern is **UNKNOWN**. Second, the hosting/encryption coupling is real: the redirect option "only works for hosted encryption", so an entity advertising its own PII key for end-to-end encryption must self-host its DID Document — **INFERRED** by reading the two pages together; the docs never state this reconciliation explicitly.

#### 5.1.2 Key roles match the docs; the live PII key spelling drifts — CONFIRMED with caveat (I2)

The documented key-role split is verbatim: "Ed25519VerificationKey2018 for signing, X25519KeyAgreementKey2019 for DIDcomm message encryption and EcdsaSecp256r1VerificationKey2019 for PII encryption" ([diddocs-explained](https://devx.notabene.id/docs/diddocs-explained.md), fetched 2026-09-24), with a dedicated fragment convention: "Our chosen approach is to introduce a `#PII` extension to the key agreement `"id"` in the DIDDoc… Make sure the "id" ends with \#pii" ([key-management-in-diddocs](https://devx.notabene.id/docs/key-management-in-diddocs.md), fetched 2026-09-24). The live DIDDoc at `vasps.id/no/did.json` preserves the curve and the convention but not the spelling: its PII verification method is `{"id":"did:web:vasps.id:no#notabene-pii","type":"JsonWebKey2020","publicKeyJwk":{"kty":"EC","crv":"P-256",…}}` — type `JsonWebKey2020` and fragment `#notabene-pii`, versus the doc sample's `EcdsaSecp256r1VerificationKey2019` and `#pii`. Both sides are quoted because the conflict is unresolved in the public record. The consequence is narrow but real: key-selection logic that locates the PII key by exact type string or exact fragment `#pii` will fail against the live document; it should match on "fragment ends with pii" and curve P-256. A second drift runs the other way: the doc sample non-standardly lists the Ed25519 signing key under `keyAgreement`, while both live DIDDocs list only X25519 and PII keys there — live practice is cleaner than the documentation.

### 5.2 DIDComm security profiles

#### 5.2.1 Five profiles; the default is the non-repudiable one — CONFIRMED (I3)

Replit's report claims that signed plaintext, sign-then-encrypt, authcrypt, and anoncrypt are distinct guarantees and that "authcrypt sender authentication is not automatically a separate non-repudiable signature." The go-didcomm repository (README and `profile.go`, `main` branch, last pushed 2026-07-28, fetched via the GitHub API 2026-09-24) exposes exactly five profiles and states the properties more precisely than the report did ([go-didcomm](https://github.com/Notabene-id/go-didcomm), fetched 2026-09-24). `ProfileSignedAnoncrypt` — the documented default — is "sign-then-encrypt: an inner EdDSA JWS wrapped in an ECDH-ES anonymous-sender JWE. Authentication is the inner signature, so it is NON-repudiable (provable to third parties)". `ProfileAuthcrypt1PUv3`/`v4` implement ECDH-1PU (draft-madden-jose-ecdh-1pu-03/-04): "the sender's static key enters the KDF, authenticating the sender at the envelope with no inner signature. Repudiable." `ProfileAnoncrypt` is ECDH-ES only, with no sender authentication; `ProfileSigned` is a signed-only JWS that "travels in the clear". Verdict: **CONFIRMED**. The implication: profile selection is a compliance decision, not a transport detail. Only the two signature-bearing profiles produce evidence a VASP could present to a third party to prove which counterparty sent a Travel Rule message; authcrypt proves sender identity to the recipient but is explicitly repudiable. Which profile protects each production message class remains **UNKNOWN** — the library default is documented, but no public artifact states that production traffic uses it.

### 5.4 PII encryption modes

#### 5.4.1 Managed mode — CONFIRMED (I6); Notabene sits inside the plaintext boundary

The managed mode is documented without ambiguity: "**Use Case:** Submit PII to be encrypted and stored locally on Notabene's platform. **Encryption Process:** Notabene encrypts data with your Entity's keys… **Data processing:** Notabene re-encrypts your data (PII) and sends it to requesting counterparties if and where applicable and not blocked" ([encryption-by-notabene](https://devx.notabene.id/docs/encryption-by-notabene.md), fetched 2026-09-24). Reuse is deliberately narrow: "PII can be reused if `txAppend` is called with both originator and beneficiary `@id`… Reuse is only for PII you created; received PII is not reused." Verdict: **CONFIRMED**. The consequence Replit drew is correct: because the platform encrypts, stores, and re-encrypts, Notabene is a data processor with structural plaintext access in this mode, and every UNKNOWN about its internal controls (HSM/KMS backing, operator access, retention, deletion) becomes part of the institution's data-protection posture.

#### 5.4.2 Customer-managed E2E, legacy escrow, and two cryptosystem generations — CONFIRMED (I7, I8)

The customer-managed mode is confirmed and, as Replit stressed, narrowly scoped: "Submit encrypted PII for end-to-end encrypted forwarding to a counterparty. This data won't be stored on your entity or the Notabene platform" ([self-encryption](https://devx.notabene.id/docs/self-encryption.md), fetched 2026-09-24), and the non-decryption claim is explicitly conditional: "when you choose for full end to end encryption we cannot decrypt PII on your behalf" ([diddocs-explained](https://devx.notabene.id/docs/diddocs-explained.md), fetched 2026-09-24). The sender encrypts to the receiver's PII key from the receiver's DIDDoc; the platform applies "message level encryption and signing, and further routing to the DIDComm endpoint" — it wraps and routes but cannot open the nested ciphertext. The legacy escrow mode is something else entirely and is labeled honestly by the vendor: every VASP has "an escrow public key that has been generated by Notabene" enabling a "pseudo end-to-end encryption flow", in which "both the originator and beneficiary can see the PII in the UI by using the 'decrypt' button" ([key-management](https://devx.notabene.id/docs/key-management.md), fetched 2026-09-24). Two PII cryptosystem generations coexist in the live doc set — the legacy `did:key` Ed25519 `pii_didkey` (Ed25519→X25519 conversion for ECDH) and the current Web-DID P-256 `#pii`/`#notabene-pii` key alongside X25519 `keyAgreement` — with no documented migration relationship (**UNKNOWN**, and a live interop risk for counterparties on different generations).

### 8.1 "What would I actually have to build" — deltas to Replit's answer

Replit's core integration answer survives the audit. The six-step minimal hosted-UX path (onboard one entity, backend-held credentials, embedded SafeConnect, server-side transform, Svix-verified webhooks, institution-gated custody execution), the full-control path, and the Phase 0–4 sequencing — hosted components first, managed PII only with privacy sign-off, no automated custody release until failure, replay, and reorg tests pass — were re-checked against the re-fetched specifications and repositories and are **CONFIRMED** as a sound reading of the public evidence ([report under audit](https://replit.com/@identityglobal/Notabene-Technical-X-Ray), fetched 2026-09-24). What changes is the estimation basis and five specific decision inputs.

#### 8.1.1 The integration surface is larger than stated: 231 total operations across both generations, eight npm packages, and Flow internal operations; V1 remains a live documented generation with a LEGACY maintenance signal

**Delta (a) — scope size.** The build surface is not "157 API operations" and "four public npm packages." It is 231 documented operations across two live generations — V2 with 105 operations on 85 paths, V1 with 126 on 90, counted as path×method (§3.1) ([V2 OpenAPI](https://node-open-api-specs.s3.eu-central-1.amazonaws.com/openapi.json), [V1 docs](https://doc.notabene.id/), fetched 2026-09-24) — eight official `@notabene/*` packages plus one provenance anomaly and two unscoped legacy packages (§6.1.2), and V2 operation groups Replit never enumerated: five Flow Internal operations (`signal`, `agent`, `status`, `authorization`, `fund`), the 8-operation Relationships API with twelve wallet-proof types, Members and invites (7), `delegateToken`, `address-ownership/discover`, `audit-log`, `public-keys`, Network discovery (4), and Transfer Checks (2) (§3.3.4). Any estimate derived from "157" understates the documented surface by 32%, and capacity planning must additionally price the 56 V1 `/integrations/*` operations (BitGo, Chainalysis, Elliptic, TRM, sanctions) that have no public V2 equivalent — an institution depending on them cannot assume a documented migration path exists.  
**Delta (b) — V1's dual signal.** V1 is simultaneously still-documented, still-served by a shipped non-deprecated npm client, and maintenance-LEGACY: notabene-nodejs received 5 commits in twelve months, all CI/dependency fixes, and the javascript-sdk deleted its V1 transformer helpers on 2026-06-30 (commit `5b0a15d`, §6.3.1) ([notabene-nodejs](https://gitlab.com/notabene/open-source/notabene-nodejs), [javascript-sdk](https://gitlab.com/notabene/open-source/javascript-sdk), fetched 2026-09-24). The migrate-now-versus-wait decision should therefore be made on the code signal, not the registry signal: no npm deprecation banner exists on any package, so the closing of the V1 compatibility window is visible only in commit history. New builds target V2; existing V1 consumers should treat the absence of a deprecation notice as a registry artifact, not a commitment.  
**Delta (c) — the Flow payout contract is confirmed buildable, with contracted caveats.** The payout create contract — required `ref` (the idempotency key), `currency`, `amount`, `customer`, `merchant`; duplicate `ref` returning HTTP 409 with `existingRef`; CAIP-19 asset selection with CAIP-10/`payto://` settlement addresses — is **CONFIRMED** at field level (§3.3.3). But the unresolved PRA conflict (quickstart: "Send only the asset field"; spec: `required: ["settlementAddress"]` — §3.3.3) and the undocumented statuses (AWAITING-YOURS, AWAITING-COUNTERPARTY, agent REPLACED/UNREACHABLE — §3.3.1) mean the buildable contract is the *documented* one, not necessarily the *deployed* one. Integrators must contract for deployed-behavior answers before implementing pay-in authorization or automated state routing.  
**Delta (d) — the micro-transfer confirmation duty is unassigned.** Replit asserted the institution verifies micro-transfers; this audit downgraded that to UNKNOWN (§5.5.2): the proof object completes as `status: "pending"` and no public document states who performs the on-chain confirmation ([self-hosted-wallet-verification](https://devx.notabene.id/docs/self-hosted-wallet-verification-1.md), fetched 2026-09-24). Until Notabene answers, assign the duty internally: the compliance queue must be staffed to watch the chain itself, and descoped only on a written platform commitment.  
**Delta (e) — jurisdiction pinning must distinguish failure modes.** Japan (JP-0) and the FATF fallback (FA-1000) are usable as published — both match their legal baselines (§4.1.5, §4.1.6). GB, EU, and SG are not: GB is trigger-stale (EUR 1,000 vs GBP 800 since 30 June 2026), the EU definitions are field-lax (a four-way pick:1 against Article 14(1)(d)'s compound requirement), and SG has an expressiveness limit (no legal-person path in the birth alternative) plus an unencoded comparator (§4.1). A pinning strategy that versions definitions per transfer must additionally overlay the EU compound limb, override the GB selector, and record comparator assumptions — "pin the vendor artifact" is sufficient only for JP and FA.

#### 8.1.2 The proprietary-vs-glue conclusion stands and is strengthened: active investment concentrates in the SafeConnect wrapper, PII cryptography, and TAP evolution — the hosted network, directory, and policy operations remain the non-reproducible core

Replit's split — proprietary difficulty in the hosted network and directory, counterparty reach, hosted SafeConnect screens, jurisdiction/presentation-definition operations, policy orchestration, and managed PII re-encryption; public glue in TAP/TAIPs, DIDComm, Web DIDs, CAIP identifiers, IVMS101-shaped payloads, OpenAPI, Svix conventions, and SDK wrappers — is **CONFIRMED**, and the code archaeology of §6.3 sharpens it from inference to measurement. Of the 219 code commits across the GitLab group's three SDK repositories in the trailing twelve months (excluding ndar's near-daily data-feed commits), 214 land in exactly two repositories: javascript-sdk (183; the SafeConnect wrapper, which contains zero screen-UI source) and pii-sdk (31; the PII cryptography, including libsodium-based ECDH-1PU, commit `42a4efc`) ([GitLab group API](https://gitlab.com/api/v4/groups/notabene%2Fopen-source/projects?include_subgroups=true&per_page=100), fetched 2026-09-24).
