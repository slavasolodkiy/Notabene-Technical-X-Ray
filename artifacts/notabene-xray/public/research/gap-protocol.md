# Protocol and cryptography gap research

Evidence date: 2026-09-24. Scope is public material only. This report distinguishes repository ownership, protocol authorship, governance, transport cryptography, application-level PII cryptography, and deployment-specific access.

## TAP specification and parser ownership/history

- **VERIFIED:** The canonical public specification is the `TransactionAuthorizationProtocol/TAIPs` GitHub repository. It is owned on GitHub by the `TransactionAuthorizationProtocol` organization, is public and non-forked, and exposes proposals, prose documentation, JSON Schemas, test vectors, contribution instructions, and a changelog. GitHub metadata dates repository creation to 2023-11-22; its earliest reachable commit is `eb807fac4189319f1a7b4504af020c680fbe92fa` (2023-12-14), authored with a `notabene.id` email. [gap-protocol-01, gap-protocol-03]
- **VERIFIED:** The repository README attributes “Transaction Authorization Protocol” to Notabene, Inc. while inviting community proposals. Therefore “open/public protocol initiated or authored by Notabene” is supported; “independent standards body owns TAP” is not. [gap-protocol-01]
- **VERIFIED:** The repository metadata identifies the root `LICENSE` as CC0-1.0, while the rendered README still says CC BY-SA 4.0. The licensing text is internally inconsistent and must not be silently resolved in favor of either statement. [gap-protocol-01, gap-protocol-03]
- **VERIFIED:** The official TypeScript implementation/types now live at `TransactionAuthorizationProtocol/tap-ts`. Public git history shows that it was extracted from `TAIPs` on 2026-05-01: the repositories share 253 commits, followed in `tap-ts` by commits explicitly preparing extraction and moving `packages/typescript` to the root. Current public surfaces include `src/tap.ts` types and `src/validator.ts`; calling this project an official types/validation implementation is supported. [gap-protocol-03, identity-13]
- **UNKNOWN:** No public repository specifically named Transaction Authorization Protocol “TAP Parser” was established. The current Notabene GitLab inventory has no such project, and web results for `tap-parser` predominantly identify the unrelated Test Anything Protocol parser. A historical renamed, transferred, deleted, or private repository remains possible. Absence from current unauthenticated inventories is not proof it never existed.
- **INFERRED:** “TAP Parser” may be an imprecise historical label for the schema/type validation surface now represented by TAIPs JSON Schemas and `tap-ts` validation. No public source found in this pass proves that name equivalence, so architecture should use the exact repository and file names instead.
- **UNKNOWN:** Public pages do not establish legal assignment of TAP intellectual property from Notabene to the GitHub organization, the organization’s legal personality, maintainer appointment rules, trademark ownership, or a governance process independent of Notabene. Open contribution and public licensing are not the same as independent ownership.

## DIDComm signing, authentication, and encryption

- **VERIFIED:** These are separate cryptographic claims:
  1. A DIDComm **signed** message uses a signature key and can provide a non-repudiable signature over plaintext.
  2. DIDComm **authcrypt** uses sender and recipient key-agreement material to provide confidentiality, integrity, and sender authentication to the recipient; that authentication is not automatically equivalent to a separately signed/non-repudiable message.
  3. DIDComm **anoncrypt** encrypts for the recipient without directly authenticating the sender.
  4. Notabene’s application-level **PII encryption** uses a dedicated recipient PII public key and can remain ciphertext inside the separately protected DIDComm message.
  [identity-02, identity-17]
- **VERIFIED:** Notabene’s public `go-didcomm` implementation exposes signed, sign-then-encrypt, authenticated-encrypted ECDH-1PU, and anonymous-encrypted profiles. Its default verified unpacking rejects unsigned or sender-anonymous input unless the caller opts out. This implementation evidence supports the distinctions above; it does not prove every production message uses every profile. [identity-17]
- **VERIFIED:** Current Notabene documentation explicitly says that, for customer-encrypted outgoing PII, the customer posts encrypted IVMS to the Notabene API and the platform then applies message-level encryption and signing and routes it. The same page says no additional PII signature is needed and distinguishes a dedicated `#pii` key from the standard communication key. Thus “the DIDComm envelope is signed/encrypted” and “the IVMS payload is separately encrypted” are not interchangeable descriptions. [identity-02]
- **INFERRED:** A hosted Notabene Node that holds the recipient’s ordinary DIDComm key-agreement private key can unwrap the outer DIDComm envelope. That does not imply it can unwrap a nested PII ciphertext encrypted only to a customer-retained `#pii` private key. Conversely, inability to decrypt the nested PII does not mean Notabene cannot read routing metadata or process the outer message.
- **UNKNOWN:** The public evidence does not prove which DIDComm profile is selected for every production TAP message, whether every production message is both separately signed and authcrypted, or whether every current V2 PII path uses the exact algorithms in the public SDK.

## Correcting “Notabene cannot decrypt”

- **VERIFIED:** The unqualified claim **“Notabene cannot decrypt” is false/misleading across the product as a whole**. Notabene documents a managed mode in which customers submit PII “to be encrypted and stored locally on Notabene’s platform”; Notabene encrypts it, validates applicable IVMS content, re-encrypts it, and sends it to counterparties. This workflow necessarily differs from customer-held-key E2E and contradicts a universal inability claim. [gap-protocol-02]
- **VERIFIED:** A narrower statement is supported for customer-managed E2E: customers encrypt IVMS to the counterparty’s dedicated PII public key, may replace the hosted `#pii` key with their own, and retain the corresponding private key. Documentation describes direct forwarding without storage on the entity or Notabene platform and says customers can choose incoming handling so Notabene cannot decrypt on their behalf. [identity-02, identity-07]
- **VERIFIED:** The E2E statement is about the nested PII and key custody, not all TAP/DIDComm data. In this mode Notabene still receives the ciphertext through its API and performs policy-controlled routing plus message-level encryption/signing. [identity-02, identity-07]
- **VERIFIED:** Legacy/current-generation boundaries matter. The older PII SDK describes three values—hosted (`0`), end-to-end (`1`), and hybrid (`2`)—using `did:key` material. Current Web-DID documentation describes ordinary signing, X25519 DIDComm key agreement, and a distinct P-256 `#pii` key. They should not be presented as one unchanged cryptosystem. [identity-01, identity-02, identity-06]
- **VERIFIED:** In the legacy escrow fallback, a counterparty without its own published PII key cannot support true E2E. Notabene documents use of a Notabene-generated escrow public key and calls the result “pseudo end-to-end”; both parties can then view PII via a UI decrypt action. It must not be grouped with customer-only-key E2E. [identity-18]
- **INFERRED:** Hybrid/selective screening deployments grant Notabene cryptographic access to at least the fields encrypted for a Notabene-managed recipient key, while other fields may remain customer/counterparty-only. The exact present-day V2 hybrid behavior was not fully specified by the fetched current docs, so this conclusion should remain deployment- and field-scoped rather than universal.
- **UNKNOWN:** Public sources do not establish production operator access controls, HSM/KMS custody, at-rest key wrapping, backup copies, subpoena/incident procedures, deletion guarantees, or whether “not stored” permits transient processing/logging. “Notabene cannot decrypt” should therefore be phrased as a documented cryptographic/key-custody property for a configured PII path, not a blanket organizational or data-access guarantee.

## Safe wording for architecture

- **VERIFIED:** Recommended: “In customer-managed E2E PII mode, and only where the sender encrypts to a receiver-controlled PII key whose private key Notabene does not hold, Notabene documents that it forwards the nested PII ciphertext and cannot decrypt it on the customer’s behalf.”
- **VERIFIED:** Recommended companion: “Notabene can process/decrypt data in managed encryption paths, and escrow/hybrid recipient sets create different access boundaries. Its hosted Nodes may also unwrap ordinary DIDComm transport envelopes even when nested PII remains customer-encrypted.”
- **UNKNOWN:** Do not claim that every TAP deployment is zero-knowledge, that the public protocol requires Notabene infrastructure, or that public protocol governance is legally independent of Notabene.
